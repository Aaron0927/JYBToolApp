# 技术方案：公版项目一键拉取全部仓库最新代码

## 1. 方案概述

在现有 `BranchSwitch` 模块中新增“拉取全部仓库”流程。用户选择公版项目主仓库并触发操作后，系统依次更新主工作区和 `fastlane/repos.yml` 中声明的依赖仓库，并将每个仓库的处理结果写入现有日志与汇总界面。

本功能只拉取当前已检出的分支，不切换分支，也不创建分支。

## 2. 模块设计

| 模块 | 职责 |
| --- | --- |
| `ReposSwitchView` | 提供“一键拉取最新代码”入口，展示执行中状态、实时日志和结果汇总。 |
| `ReposSwitchViewModel` | 发起异步任务，维护进度、按钮禁用状态和各仓库结果。 |
| `ReposYAMLService` | 读取 `repos.yml` 配置，执行工作区检查、暂存、拉取和暂存恢复。 |
| `ProcessRunner` | 执行 Git 命令并返回标准输出或可读错误。 |

在 `ReposYAMLService` 中新增 `pullAllRepositories(atProjectPath:logger:)`，返回主工作区与依赖仓库的统一结果数组。每项至少包含仓库名称、路径、状态、是否创建自动暂存及失败原因。

## 3. 执行流程

```text
选择主仓库
  -> 校验路径与 Git 仓库状态
  -> 更新主仓库
  -> 读取 fastlane/repos.yml
  -> 按配置顺序更新各依赖仓库
  -> 汇总并展示结果
```

单个仓库的更新步骤如下：

1. 获取当前分支及其 upstream；没有可拉取的 upstream 时标记为跳过。
2. 使用 `git status --porcelain` 检查已跟踪和未跟踪改动。
3. 如工作区不干净，执行 `git stash push --include-untracked`，并保存本次新建 stash 的准确引用。
4. 执行 `git pull --ff-only`，避免工具在后台自动创建合并提交。
5. 如本次创建了 stash，使用保存的引用执行恢复。恢复成功后再删除该 stash；若恢复冲突，则保留 stash 并标记失败，提示用户手动处理。

主工作区更新完成后再读取 `fastlane/repos.yml`，确保基于最新配置处理依赖仓库。依赖仓库按配置顺序串行更新：单个失败只影响自身，流程继续处理后续仓库。

## 4. 异常与安全策略

- 主仓库路径无效、不是 Git 仓库或无法读取子模块配置时，终止流程并给出明确错误。
- 远程分支不存在、未配置 upstream 或仓库处于 detached HEAD 时，跳过该仓库并记录原因。
- `pull --ff-only` 失败时不丢弃本地提交或改动；如已自动暂存，仍尝试恢复该 stash。
- stash 恢复冲突时，不执行 `stash drop`，保留暂存内容及其引用供用户处理。
- 所有 Git 命令在后台任务中执行，UI 状态和日志回到主线程更新；执行期间禁用重复触发。

## 5. 日志与结果

沿用 `LogManager` 输出“开始、暂存、拉取、恢复、成功、跳过、失败”日志。完成后按成功、失败、跳过数量展示汇总，并为失败和跳过项保留仓库名称、路径及原因。

## 6. 测试方案

为 `GitModuleService` 注入可替换的 `ProcessRunner`，以单元测试验证命令顺序和结果映射：

- 干净仓库直接拉取成功。
- 有已跟踪或未跟踪改动时，先暂存、拉取、再恢复。
- 无 upstream、远程分支不存在和 detached HEAD 被正确跳过。
- 拉取失败后仍恢复本次自动暂存。
- stash 恢复失败时保留 stash 并返回可处理的错误。
- 单个依赖仓库失败不阻断后续仓库。

实现完成后运行相关单元测试及项目既有测试命令，并通过 `git diff --check` 检查改动。

## 7. 实施边界

- 本期不处理嵌套仓库、远程仓库认证配置或自动解决 Git 冲突。
- 本期不改变任何仓库当前分支，也不自动提交、推送或丢弃用户改动。
